# 已打开的恢复资源

[English](opened-restore-resources.md)

## 背景

Firecracker 通常通过重新打开根盘和客户机内存路径来恢复已捕获的虚拟机。如果路径在
打开前被重命名或替换，重新打开可能得到另一个对象；这种方式也无法让存储实现把已经
打开并核验的对象直接交给 Blaze。

因此，Blaze 允许恢复请求携带一组可选的、带类型的已打开附件。未提供附件时，原有的
文件数据面路径仍是默认路径，行为保持不变。

`ProviderCapabilities` 通过 `opened_template_restore_resources`、
`opened_checkpoint_restore_resources` 和 `opened_suspension_restore_resources`，分别为
模板准备、检查点恢复和休眠恢复声明这项权限。每个字段表示相应操作可能返回已打开附件，
并不要求每次成功调用都必须返回附件。一项操作的声明不能授权另外两项操作返回已打开
附件。

## 合同

每组附件绑定一个沙箱、一个非零租约标识和一个正数租约代次。每个附件声明：

- 唯一的后端角色：根盘或客户机内存；
- 一个以读写方式打开、并独占转交给单个运行后端所有者的描述符；
- 普通文件、字符设备或块设备的对象类型；
- 非零且按页对齐的逻辑范围；
- 捕获的根盘需要固定路径时，由调用方预先准备的使用路径。

Blaze 在启动 Firecracker 前，把每项声明与从已打开描述符读取的事实进行核对。重复
角色、过期的沙箱绑定、不同角色引用同一对象、访问方式或对象类型不符、无效逻辑范围，
以及没有同时以可读、可写方式打开的描述符都会被拒绝。

在 Linux 上，Blaze 只允许经过核验的描述符跨越 `exec`。根盘会在子进程隔离的挂载
命名空间中绑定到捕获时使用的路径；客户机内存描述符以 `/proc/self/fd/<编号>` 的形式
交给 Firecracker。Blaze 在后端所有者的整个生命周期中持有附件集合，避免 Firecracker
仍在使用资源时提前关闭描述符。

## 范围

本合同只改变 Firecracker 的恢复输入和资源所有权。提供者选择和资源租约由
[构建时数据面提供者](build-time-data-plane-providers_zh.md)定义。重启接管、检查点
所有权、休眠和可复用容量分别属于独立的可选合同，参见
[提供者重启核对](provider-reconciliation_zh.md)、
[提供者持有的检查点](provider-checkpoints_zh.md)、
[提供者持有的休眠数据](provider-suspension_zh.md)和
[提供者数据面容量](provider-capacity_zh.md)。

目前只有 Firecracker 恢复适配器声明能够消费这些附件。对于每项选中的操作，Blaze 会
在提供者发生变更前检查相应能力；如果提供者可能返回附件，而运行后端不能消费附件，
请求会被拒绝。提供者调用返回后，守护进程与一致性软件包都会使用同一项操作能力校验
结果；未声明相应能力却返回已打开附件会被视为无效响应。声明能力后仍可返回路径型资源。
