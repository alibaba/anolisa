# 提供者重启核对

[English](provider-reconciliation.md)

## 范围

只有构建时提供者实现 `DataPlaneInventory`，并且以下三份所有权账本完全一致时，Blaze
才会在守护进程重启后接管提供者持有的沙箱：

1. 持久化的公开沙箱记录；
2. 一份不可变的提供者资源清单快照；
3. 存活后端的准确身份。

该接口是 `DataPlaneProvider` 的可选扩展。未实现它的提供者采用标准的故障关闭清理
流程，Blaze 不会把它静默当成可接管实现。

## 持久所有权

每个提供者沙箱记录都保存提供者实例、请求、操作、租约、初始代次、当前代次、租约
状态，以及根文件系统和客户机内存范围。Blaze 会在转换发生时分别持久化 `Prepared`、
`Committed`、`Finalized`、`Stopped` 和 `Released`。

在发布公开 `Running` 状态前，Blaze 还会持久化接管后端所需的运行证据。对 Firecracker
而言，这包括 PID、Linux 进程启动时钟、冻结的后端版本，以及客户机传输、网络槽位和
控制台日志所有权。PID 会被内核复用，不能单独作为进程身份。

## 资源清单合同

`begin_inventory` 冻结一次提供者视图，随后 Blaze 按有界分页读取该快照。以下情况均会
被拒绝：

- 快照属于另一个提供者实例；
- 标识为空或发生变化；
- 租约标识重复；
- 页面超限、游标重复或总量超过全局安全上限；
- 当前代次早于初始代次。

无效清单会导致启动失败。Blaze 不会在提供者视图不完整或自相矛盾时开放 API 套接字。

在已经持久化的替换事务期间，多份租约可以暂时指向同一个沙箱，但这些租约不能互换：
只有与公开账本中活动租约或替换租约完全一致的记录才可匹配，无法解释的额外租约全部
进入隔离。

## 接管与隔离

Blaze 只接管满足全部条件的对象：公开状态为 `Running`、没有未完成操作、持久记录说明
后端正在运行、存在完整后端运行证据，并且提供者清单与持久记录中的 `Committed` 或
`Finalized` 租约完全相同。Firecracker 还必须在接管前证明进程启动时钟、沙箱环境
标识、PID 交接文件、API 可响应性、冻结版本以及网络命名空间所有权。

后端身份和客户机就绪均得到证明后，Blaze 才要求提供者接管准确租约。提供者必须保留
全部标识，只增加一个代次，并返回 `Finalized`；Blaze 在重新服务沙箱前持久化该结果。

启动过程会先收敛持久转换日志、重试旧内容回收，并清理已知的中断生命周期事务。完成
这些步骤后仍存在的真实不一致才按故障关闭处理：Blaze 要求提供者隔离保留资源，在能够
证明所有权时停止后端，并把公开沙箱标为 `RecoveryRequired`。只有提供者记录、没有公开
所有者的租约也会被隔离。Blaze 不会猜测所有权、按路径接管，也不会使用不可信标识释放
资源。

## 崩溃边界

处理顺序有意采用非对称设计：

| 崩溃位置 | 崩溃后的持久证据 | 重启动作 |
|---|---|---|
| 提供者已准备，后端未启动 | `Prepared` 租约和操作日志 | 收敛日志并清理，绝不接管 |
| 后端已启动，公开状态尚未运行 | 租约和后端身份 | 收敛已知事务并清理，绝不发布运行状态 |
| 公开状态已运行，提供者已提交 | 准确 `Committed` 租约和后端身份 | 完成接管并转为 `Finalized` |
| 公开状态已运行，提供者已完成 | 准确 `Finalized` 租约和后端身份 | 用新代次重新接管 |
| 提供者接管成功，公开持久化失败 | 转换预写日志保存准确前态和目标状态 | 检查提供者、持久化准确后继状态并继续接管 |

`OutcomeUnknown` 不是成功。实现必须保留足够证据，使后续 `inspect` 或资源清单遍历能够
消除不确定性。

## 验证边界

一致性软件包会核验资源清单标识和严格的核对转换。单元测试覆盖已完成租约接管、从已
提交崩溃点完成接管，以及身份漂移隔离。生产提供者还必须用真实资源和真实 Linux 后端
验证重启行为，包括进程号复用、陈旧网络状态、响应丢失和重复核对。
