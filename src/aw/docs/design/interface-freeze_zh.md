# ADR AW 接口冻结基线

[English](interface-freeze.md) · [Schema 逐项说明](schema-reference_zh.md)

**提议，待接口评审。** 本次新增独立的合同组件，现有组件继续按原有路径运行。这组资源要在评审通过后才能成为稳定协议；目前的测试只验证合同一致性。

## 问题

Agent 框架留给扩展的权限各不相同。工具包装器可能允许等待并替换返回值，同步转换函数只能在返回前处理指定字段，事件观察器则只负责接收通知。即使扩展已经检查过参数，后续插件也可能再次修改它。因此，每个 adapter 都需要说明自己在哪个位置介入，以及能在这个位置做什么。

调用成功之后，还需要分清结果停在了哪里。Provider 生成候选，只能证明候选存在；确认本地历史或模型请求使用了它，需要在相应位置另取证据。进程管理也有类似的问题，PID 可能被复用，观察进程的人未必拥有控制权。状态操作超时后，则要先查清是否已经生效，再决定下一步。

本次拟冻结能力合同及其校验规则，明确谁有权作出决定、记录如何关联、结果能够证明什么。框架各自的 hook 名称和组件 RPC 继续由原实现维护。

## 决策与职责

| 层 | 承担的职责 | 交付的事实 |
| --- | --- | --- |
| 原生 adapter | 识别可操作边界，映射原生身份，提取文本槽位，保留外围结果，捕获最终观测 | boundary、scope、adoption |
| AW Core | 根据策略与版本协商选择能力，解释结果，要求相应环境动作 | invocation、已校验候选或决策 |
| Provider Host | 依 manifest 映射原生协议，限制调用预算，规范化成功与失败 | receipt 与独立 output |
| 组件 Provider | 执行压缩、检查等具体算法 | candidate、inspection、decision |
| 环境执行器 / 原始所有者 | 最终工具派发、进程生命周期及状态动作；执行前验证授权与当前代际 | 最终结果、runtime binding、operation 状态 |
| Ledger | 持久化并索引事实，约束重复写入，提供读取和确认 | 可追溯的证据记录 |

本次交付上表各层之间的 Schema 和纯校验函数。Rust crate 提供参考实现；其他语言可以按同一合同编写 adapter。进程内调用、stdio 和 HTTP 都可以作为传输方式，选择留给接入层。

Tokenless 等组件继续维护自己的请求、响应和 manifest，Host 负责把它们映射到 AW 能力合同。映射需要核对字段含义及失败行为，并通过接入测试。压缩器的命令行细节留在组件侧，Agent 会话的写入权留在原生环境。

## 此次补齐的缺口

| 问题 | 对应资源 / 校验 | 可接受的边界 |
| --- | --- | --- |
| 原生扩展权限不明确 | `boundary-descriptor/v1` | 明确等待方式、修改权、最终守卫、证明位置、Ledger 顺序 |
| 进程识别与控制混用 | `runtime-binding/v1`、`control-grant/v1` | PID 留在原生管理器，代际防复用，控制需所有者授权 |
| 调用与会话混淆 | `common/v1` scope、`capability-invocation/v1` | execution context 与可选 session 分离；工具调用绑定 turn/tool ID |
| 不同版本被静默混用 | schema 引用、`provider-descriptor/v1` | ID 和文件摘要必须同时匹配，未支持版本明确拒绝 |
| 压缩后的可恢复性含糊 | projection v2 | 模式、解码器或 resolver、源摘要与有效期均明确；采用前独立回读 |
| 候选被计为节省 | `provider-receipt/v1`、`context-adoption/v1` | 只有已验证且已记账的采用才能派生可归因节省 |
| 扫描范围和语言不清楚 | content/code/command inspect v2 | 输入字节、扫描字节、完整性、规则集、实际语言分开表达 |
| 检查后参数仍能改变 | `execution-intent/v1` | 完整参数字节、目标、cwd、环境、执行器与 OS 策略共同绑定 |
| 缺少能力执行顺序 | `capability-plan/v1`、`plan-execution/v1` | Core 固定步骤、路由与失败策略，完整记录终态 |
| 把 hook 视为系统防护 | `os-protection-binding/v1` | 独立权威提供实际控制覆盖，必需控制不足则不派发 |
| 超时后重复执行状态动作 | `operation-record/v1` | 持久化审批、幂等键和 uncertain 查询收敛；禁止直接重试 |

## 框架兼容方式

adapter 按原生入口的实际权限接入，支持范围由边界描述决定。

| 原生入口类型 | 可接入方式 | 必须保留的限制 |
| --- | --- | --- |
| 可等待的工具包装器 | 派发前检查，返回后投影；最终返回位置独立观测 | 下游仍能修改时，该位置不能称为最终边界 |
| 同步结果转换函数 | 同步完成已经准备好的替换或有界同步调用 | 不能假设 Promise 会被等待，也不能把异步写入称为交付前持久化 |
| 纯事件观察器 | 记录观测，声明 `observe_only` | 不声明阻断、替换或 `required_before_delivery` |
| 多内容块工具结果 | adapter 为一个文本槽位创建 artifact | 图片、错误、结构化字段和其他块必须保持原状 |
| 子 Agent / 多会话运行时 | 为每个执行上下文建立 scope 和 parent 关系 | 不把一个 OS 进程等同于一个会话 |
| 模型请求代理 | 在 `before_model` 或 `proxy` 位置独立处理 | 请求可见不等于能阻断此前工具执行 |

AW 保留原生事件机制与消息结构，同时统一 AW 能力计划、决策组合及关键边界的顺序约束。adapter 必须证明声明的边界与组合顺序成立；缺失最终观测时使用 `unverified`。执行计划和 OS 防护的具体合同见本文后续章节。

## 冻结与扩展政策

评审接受后，版本约束同时覆盖资源文件字节和字段语义，状态机及 AW JSON 编码规则也随版本固定。当前对象和枚举都采用封闭定义，增加可选字段或枚举值也可能让旧读取器失败。因此，扩展要发布新的 Schema ID，由调用双方重新协商；旧资源保持原样。

能力输入输出采用 v2，将更严格的恢复和扫描覆盖规则与实验性 v1 区分开。新增协调与证据资源从 v1 开始编号。这些编号用于识别合同，尚不构成稳定发布承诺。当前库没有旧 v1 校验器或自动转换代码，现有调用继续使用原协议。

新能力以独立 capability 名称与输入输出 Schema 加入目录，不改变 invocation 外壳。当前参考校验器只接受四个已登记能力；Provider 声明一个新名字不会自动获得执行权。`driver`、`lifecycle`、规则集与 decoder/resolver 的名称也必须在 Host 或 adapter 的受信注册表协商，未知值拒绝，不能作为动态加载路径。

具体传输和 SDK 编程模型留待接入时评审，Provider 的启动、调度和恢复方式也尚未固定。审批 UI、Ledger 存储及凭证格式由各自实现负责。二进制或多模态投影、状态能力 payload、OS 策略执行和 Token 估算算法都不在本次冻结范围内。当前合同只记录这些模块之间需要核对的身份、版本和证据。`operation-record` 定义通用操作状态机，State Provider 仍需补充具体能力合同。

## 逐步迁移与验收

本分支已提供第 0 步的实现，接口评审仍待完成。第 1 至 6 步需要后续集成与验收。

| 步骤 | 改动范围 | 必须通过的验证 |
| --- | --- | --- |
| 0 合同基线 | 新 `src/aw`、Schema、语义校验、文档 | 所有 payload 样例有效，反例拒绝，跨语言摘要一致，评审接受 |
| 1 入口观测 | 在 cosh-ng 入口建立运行时身份和代际 | 正常退出、重新启动、外部附着、进程标识复用不串联旧状态；不提升控制权 |
| 2 只读能力调用 | Host 接一个原生 Provider，Core 做版本协商 | input → output → receipt 同一次调用关联；故障、超时、无结果保持真实 |
| 3 投影采用 | 一个具备替换与观测能力的原生 adapter | 保留其他内容块，回读源内容，验证最终边界，无节省和后续覆盖不计节省 |
| 4 执行前安全 | 有序计划、最终执行器及独立 OS 防护 | 拒绝不可覆盖；输入或策略变更使旧结果失效；绕过 hook 的系统访问仍受限制 |
| 5 状态操作 | 评审独立状态 payload、审批及恢复实现 | 幂等、重启恢复、超时 uncertain、过期审批、代际变更和查询收敛 |
| 6 多框架兼容 | 每个 adapter 发布边界描述和兼容测试 | 至少覆盖可等待、同步、观察三类入口；不将某一类的能力套到另一类 |

进程崩溃与 Ledger 提交失败必须在后续原生集成中注入验证。合同单测不会替代这些测试。第一版 Rust 公共 API、时间预算口径、资源上限、恢复有效期及 operation 状态机均需评审者确认后才接受为稳定语义。

## 取舍

一个有大小限制的 UTF-8 文本槽位，足以承接当前压缩和检查能力，也能保留外围框架消息。未知字段会被严格拒绝，便于及早发现调用双方对合同的理解不一致；相应的代价是每次扩展都需要协商。JSON 和离线 Schema 方便不同语言实现，多个记录之间的关系则由语义校验器检查，并配有反例测试。

观察入口保留观察权限，进程生命周期仍由原始所有者管理。后续加入控制能力时，需要由原生实现验证授权，并保证最终检查与动作不可被其他变更打断。

## 执行顺序与原生事件系统

一个原生边界事件进入 Core 后，由 Core 确定本次 AW 能力的执行顺序。adapter 和环境执行器负责让这个顺序在框架中成立。框架继续使用自己的事件机制和消息结构，Provider 通过 Core 的计划被调用，避免各自订阅 hook 时出现顺序冲突。

DSH 的 Waterfall 是带返回值和 continuation 的组合调用链，原生工具运行时显式等待链的决策。最终 guard 与不可变结果观察是分开的入口，这种分层适合作为原生 adapter 的参考；AW 不要求其他框架安装相同的事件总线。[DSH 扩展说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/extension-cookbook.md)

本基线采用 `capability-plan/v1` 的有序 steps，复用 Core 决定能力、Provider 选择方式和失败策略的职责。计划包含 event_id、scope、版本、原文摘要及已解析的 Provider 身份；所有路由在调用前确定，处理过程中不因插件加载顺序改变计划。初版每步读取同一份 boundary_source，检查原文不会意外变成检查压缩候选。投影必须是最后一步且最多一次，源检查先于候选生成。任意 DAG、候选再次变换、多轮重试和动态插入步骤不属于本 profile。

对于同一个计划，步骤依次完成；不同 event_id 可以独立并发。`all_distinct_providers` 要求本步所有已选择实现各调用一次；`exactly_one` 最多选择一个实现。路由为空可以记录为 gap，不假装 Provider 已被调用。计划中的 required 表示必须取得可用结果，不代表某个内容 finding 自动获得阻断权限；本 profile 的 content/code 检查产生事实，command 检查承担派发门禁。

```text
原生边界事件 → Core 固定计划
  → 按序运行能力，关联 Invocation 与 Receipt
  → 汇总整个计划的终态
  → 环境最终守卫 → 最终派发 / 实际采用
```

在普通调用链中，插件即使返回 allow，也可能没有调用 next，导致后续检查被跳过。必需的 command 步骤因此要由计划完整性来约束，不能配置为 optional，失败后也不能使用 record_gap_and_continue。任一 command verdict 为 warn/deny，本计划都不能直接派发；初版没有隐式审批覆盖，需要新的明确决策流程。强制拒绝、取消或保留原文一旦成为终态，后续步骤必须标记 skipped；后来的 allow 不能改写它。

观察步骤只有在显式 optional 且配置 record_gap_and_continue 时才能缺失后继续。reject_plan 在执行前表示不派发，在工具返回后表示保留原文；投影没有可用候选时不能伪造采用。计划 proceed 仅代表允许进入下一原生阶段，不表示候选已采用、工具已执行或 OS 已经允许了实际系统调用。

`plan-execution/v1` 记录全部步骤，包括 gap、skipped 和 cancelled；只有实际调用才引用 Provider Receipt。started_sequence/settled_sequence 来自同一 Core 的有序日志，验证前一步已结束再开始下一步，不比较不同机器的墙钟来推断顺序。写入者必须认证日志、持久化顺序，并保证每个 event_id 的实际工具派发只被领取一次。纯校验函数重复返回 Ok 不构成再次执行授权。

## OS 层作为独立系统防护

工具执行同时受 AW 决策和环境最终输入守卫约束，系统资源访问还要经过持续生效的 OS 限制。OS 防护应在不可信执行开始前建立，覆盖策略指定的实际执行主体及子执行范围；它不依赖 Agent 是否调用了 AW hook。AW 的 allow 不得放宽已安装的 OS 规则，OS 限制也不能反过来让已经被 AW 拒绝的工具继续派发。

```text
                         持续生效的 OS 访问限制
原生参数 → AW 检查 → 最终意图复核 → 工具执行 → 系统资源访问
                         ↑                 ↑
                   检查防护绑定       内核/系统执行器独立限制
```

`capability-plan.os_requirement` 指定固定策略摘要及必需的版本化控制项，例如 `filesystem.access/v1`。`execution-intent.protection_policy_digest` 将同一策略绑定到最终执行。可信系统管理器提供 `os-protection-binding/v1`，记录目标与运行实例、签发权威、状态、控制项覆盖、实现机制、时效和独立证据。controller 必须使用预配置的可信权威身份验证来源，不能接受 Provider 自签的“enforced”声明。

`validate_dispatch` 只有在整个计划允许、当前意图未变化、绑定仍有效、策略和目标匹配、每个必需控制项均为 enforced 时才通过。缺失防护、仅声明支持、内核不支持必需控制项、旧代际或过期证据均拒绝准入。该执行 profile 不允许静默降级为无 OS 防护；确需不同保障级别时，应先经过独立策略评审和显式协商。

合同记录的是控制项和策略身份，不把 Landlock、seccomp 或任何特定系统机制写死为唯一实现。Landlock 对具体进程执行访问限制；seccomp 过滤系统调用，本身不是完整沙箱。实际覆盖需由实现根据内核能力验证，不能由机制名称推导“所有访问均受保护”。[Landlock](https://docs.kernel.org/userspace-api/landlock.html)、[seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)

控制项的精确访问范围由受信策略目录及匹配的 policy_digest 解释。实现必须检查线程/子进程、继承的权限与资源句柄、替代执行路径，以及保护权威与不可信插件之间的权限隔离。OS 防护是否生效，需要系统层提供证据，hook 中的布尔值无法证明这一点。OS 实际阻断是环境运行事实，不能记成压缩 Provider 的拒绝或仅凭一个工具错误码推断。

本次提供接口、纯校验器和合成合同测试，系统防护仍需实机验收。验收时先跳过或短路 hook，确认策略禁止的资源依然无法访问，再检查子进程和替代执行路径是否受同样约束。权限不足或必需控制缺失时，绑定不能报告 active。还要验证策略变更能否使旧意图失效，并把实际拒绝证据关联到当前目标。OS 限制覆盖已配置的系统行为，业务语义风险仍需要 AW 检查。
